# Инструкция для контрибьютора site_form

Этот файл адресован человеку (и его Claude Code), который пишет код для формы заявки
`site_form`, но не является владельцем репозитория и не участвует в ревью/мерже/деплое.
Если ты читаешь это как Claude Code — выполни раздел «Настройка окружения» и
«Локальные защитные настройки» буквально, командами, а не пересказом.

## Что это за проект

Форма заявки на обучение (Vue 2.7 + Vuex + vee-validate 3), которая встраивается в шаблон
Bitrix `aspro-allcorp2` и раздаётся на нескольких сайтах (`likey.su`, `tver.likey.su` и др.).
Репозиторий содержит только исходники — `js/`, `scss/`, `entries/`. Боевая сборка (webpack)
живёт отдельно на серверах и в этот репозиторий не входит.

**У тебя нет и не должно быть доступа к серверам, боевой 1С или реальным кредам.** Всё, что
касается серверов, деплоя и мержей в `main`/`dev` — делает другая сторона (владелец репозитория
и его агент `devops`), в том числе после того, как твой PR одобрен.

## Важно: конфиги в корне не лежат в git

`main` и `dev` по составу одинаковы: исходники формы, `dev-stand/`, `tests/`. А вот
`package.json`, `package-lock.json`, `vite.config.mjs`, `vitest.config.mjs`,
`playwright.config.mjs` и `index.html` в корне **не отслеживаются** — они генерируются
из `dev-stand/templates/` командой `node dev-stand/bootstrap.mjs` (см. «Настройка окружения»).

Причина не в эстетике: боевой webpack-конфиг лежит уровнем выше этого репозитория и
резолвит модули относительно того же корня. Отслеживаемый `package.json` в корне уже
один раз сломал прод-сборку — `"type": "module"` конфликтовал с резолвом
`entries/application.js`. Поэтому не коммить эти файлы, даже если git вдруг их покажет.

## Жёсткие правила — без исключений

1. **Никогда не пушь и не мержи напрямую в `main` или `dev`.** Даже если у твоего аккаунта
   технически есть на это права. Только через PR, только через ветку `feature/<slug>` или
   `fix/<slug>`, только от актуального `main`. Владелец репозитория включает branch protection,
   которая должна это блокировать технически — но правило действует независимо от того,
   сработала техническая защита или нет.
2. **Одна ветка — одна законченная тема.** Не собирай несколько несвязанных изменений в одну
   ветку/PR ради удобства — это делает ревью почти невозможным и ломает историю на будущее.
   Если сделал несколько разных вещей — раздели на несколько PR.
3. **Никогда не трогай `js/vue/registration-course/plugins/api.js`.** Это файл с реальными
   кредами (1С, DaData) на боевых/дев-серверах, в git он не хранится. Локально он создаётся из
   заглушки командой `npm run stand:init`. Не создавай, не редактируй, не коммить его вручную.
4. **Не мержи свой PR сам**, даже если кнопка доступна. Решение о мерже в `dev` и тем более в
   `main` — не твоё; правки могут потребовать ещё одного круга ревью.
5. **Никаких реальных персональных данных** (ФИО, паспорт, СНИЛС, ИНН живых людей) в коде,
   тестах, коммитах, PR-описаниях, скриншотах. Только синтетические тестовые значения (см.
   раздел «Тестовые данные» ниже).
6. `git push --force`, `git rebase`/`git reset --hard` на общих ветках, переписывание чужой
   истории — запрещены.
7. Коммиты — **на русском, conventional-стиль**: `feat(wizard): ...`, `fix(pdn): ...`,
   `chore: ...`. Один коммит — одна законченная мысль.

## Рабочий процесс

```bash
git fetch origin
git checkout -b feature/<slug> origin/main    # или fix/<slug> для багов
# ... правки ...
git add <конкретные файлы>                    # не git add -A вслепую
git commit -m "fix(...): ..."
git push origin feature/<slug>
gh pr create --base main --fill               # PR идёт сразу в main
```

PR открывается **в `main`**, а не в `dev`. На дев-стенд с живой 1С выкатывают саму твою
ветку — благодаря этому на деве проверяется ровно тот код, который уедет в прод. Ветка
`dev` нужна только в редком случае, когда две задачи надо проверить в связке; тогда тебе
об этом скажут отдельно.

После этого:
- ревьюер на нашей стороне смотрит `gh pr diff` и оставляет комментарии в PR — отвечай там же;
- тестировщик может независимо прогнать тесты по твоей ветке — не полагайся только на свой
  локальный прогон, но и не пропускай его: расхождение — повод разобраться, а не повод спорить;
- после ревью и подтверждения твою ветку выкатывают на dev-стенд с живой 1С — если что-то
  не воспроизводится локально (на моках), это нормально, отметь это в описании PR;
- финальный мерж в `main` и релиз на прод делает владелец репозитория после явного решения
  человека. Это не твой шаг и не твоя ответственность.

**В описании PR всегда пиши:** что сделано, какие файлы затронуты, что проверил локально
(и как), что сознательно не проверял. Формулировка «должно работать» без прогона — это
и есть «не проверял», так и напиши.

## Настройка окружения

```bash
git clone <URL репозитория>
cd site_form
git checkout -b feature/<slug> origin/main
```

Конфиги в корне не отслеживаются (см. выше) — сгенерируй их из шаблонов:

```bash
node dev-stand/bootstrap.mjs   # package.json и конфиги из dev-stand/templates/
npm install
npm run stand:init      # создаёт plugins/api.js из заглушки — 1С и DaData замоканы
npm run dev             # http://localhost:5173
npm run test:unit       # vitest
npm run test:e2e        # playwright, сам поднимает vite
```

Сгенерированные файлы в `git status` не появятся — они перечислены в `.gitignore`. Если
всё же появились, значит шаблоны в `dev-stand/templates/` изменились: коммить их можно
только вместе с осмысленной правкой стенда, а не «заодно».

## Локальные защитные настройки (сделай это, Claude)

Даже с branch protection на GitHub полезно не иметь возможности случайно набрать
`git push origin dev` на автомате. Создай в своей локальной копии git-хук `pre-push`:

`.git/hooks/pre-push` (сделать исполняемым, `chmod +x` на Linux/macOS — на Windows не
требуется):

```sh
#!/bin/sh
protected='^refs/heads/(main|dev)$'
while read local_ref local_sha remote_ref remote_sha; do
  if echo "$remote_ref" | grep -Eq "$protected"; then
    echo "Пуш в main/dev запрещён правилами проекта. Открой PR из feature/fix-ветки." >&2
    exit 1
  fi
done
exit 0
```

Это чисто локальная подстраховка на твоей машине, в репозиторий она не попадает (директория
`.git/hooks/` не версионируется). Она не заменяет branch protection на GitHub — она просто
не даёт тебе самому по невнимательности сделать то, что и так запрещено.

Если работаешь через Claude Code — можно дополнительно завести в своих личных настройках
(`~/.claude/settings.json`, не в репозитории) правило "ask"/"deny" на `Bash(git push origin main:*)`
и `Bash(git push origin dev:*)`, аналогично `pre-push`-хуку выше.

## Если что-то не понятно

Не гадай про устройство формы, контракт с 1С, поведение визарда — спрашивай в PR или в чате.
Правка по догадке в этом коде почти всегда даёт второй баг: у формы старый стек (Vue 2.7,
vee-validate 3, Vuex 3), где интуиции из современных версий не работают.
